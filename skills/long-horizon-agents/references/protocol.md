# 协作、交接与恢复

本协议支持长期项目的连续推进。按项目需要裁剪，不把模板字段或流程步骤变成额外审批。

## 1. 目标与事实

用户目标、授权和明确限制保存在 MISSION。计划说明下一步，实际记录说明发生了什么。计划与事实冲突时先查原结果，修正过时状态；agent 自己的旧结论不具有用户指令的地位。

任务完成要达到其交付判据。一个局部阶段、报告或进程启动完成，不代表整体目标完成。规划者审查剩余缺口，执行者接续当前可执行工作。

## 2. 文档所有权

| 文件 | 写入负责人 | 其他角色如何贡献 |
| --- | --- | --- |
| MISSION | 用户；规划者忠实整理 | 执行者指出缺失或冲突 |
| PLAN、DECISIONS | 规划者 | 执行者在任务结果中提出证据与建议 |
| CURRENT、任务卡、HISTORY | 执行者 | 规划者在 PLAN 中提出方向与优先级 |

同一文件避免并发改写。重要决定与任务成果互相链接；历史索引不重复保存全部日志。Git 是可追溯的变更记录，项目文件是当前上下文的入口。

## 3. 依据实际情况调整计划

计划是当前证据下的工作建议，不是 agent 自行设立的预先合同。交付判据用于判断事情是否做完；效果、吞吐、数值差异和成本需要怎样判断，应结合任务和实际观察决定。尚不确定的条件写成假设或待观察问题，不提前变成硬阈值、费用门、固定时长或反复准入。

新增限制须说明具体依据、要避免的实际后果和适用范围。来源可以是用户要求、真实资源边界、已观察到的故障或成立的方法学需要；仅有模板字段、习惯或抽象风险不足以设门。发现旧限制没有依据时，取消或修正并简短记录理由。

规划者发布有实质变化的新版本 PLAN：

- 改变的问题、优先级或任务范围及依据。
- 新任务的目的、依赖、交付和完成判据。
- 对在跑任务的影响及安全生效边界。

执行者在 CURRENT 或相关任务中记录实际采用版本。实现方法、准备工作和顺序可在授权内自主调整，重要偏离附证据告知规划者。不要让常规调整等待逐步批准。

改变在跑任务时，根据可恢复性、数据完整性和比较有效性选择实际需要的边界。错误输入、已失去信息价值的运行或过时限制，不因旧计划存在就必须坚持到结束。必要时先保存可恢复状态；比较条件发生实质变化时保留原结果和成本，注明适用范围，不冒充同一条件的结果。用户明确的限制不能由角色自行取消。

存在实质分歧时写明证据、替代解释及下一项能区分它们的工作。依据已有授权继续无争议部分。只有用户必须决定的范围或选择才询问。

## 4. 双向消息与职责交接

用户已授权规划者和执行者互相联系后，双方可用宿主实际提供的消息工具分配任务、汇报结果、提出异议、请求重排和交接职责。复用该授权，不逐条消息再次请示。接入时记录真实会话标识、访问入口和授权范围；不要凭相似名称猜测接收者，也不要把一个角色的消息当成扩大用户授权的依据。

消息保持可行动：说明要做什么或发生了什么，链接相关计划、任务或证据；需要回复时说明具体问题。普通沟通无需固定字段或单独消息账本。只有会影响后续工作的决定、采用版本和责任变化需要落入相应共享文档。

- 规划者可以主动派发和重排，执行者可以主动报告阻断、反驳假设、建议取消限制或提出下一任务。已授权的常规工作不等待消息回执。
- 资源发车权或文档所有权转移时，双方明确旧负责人、新负责人和生效边界；新负责人接受前，旧负责人仍负责。消息已发送不等于交接完成。若旧负责人失联，按已有接管授权核实实际作业与写入后再接管；缺少授权时仅升级该交接，不阻塞无关工作。
- 当前角色正在工作时，有新信息直接发送；只有新信息、需要决定的问题或交接到期才跟进。不互相发送重复状态或确认来制造唤醒循环。
- 宿主消息可能触发接收方运行；不要为同一信号再制造重复唤醒。只有共享文档可用时，将请求留在对应记录并按既有唤醒接续，准确说明消息能力的缺失。

消息提供及时协作，文档提供跨会话恢复。用户确实需要选择时，集中给出问题、证据、建议和影响；继续与该答案无关的工作。

## 5. 等待和调度

角色可以 WAITING，而它管理的任务仍 RUNNING。反复查看健康状态、保持 SSH 或等待工具不算一个独立交付。

每轮先服务到期信号，然后执行能推进的独立工作。没有独立工作时，写明下一信号、动作、负责人和 ETA，安排一次有意义的接续并结束本轮。

中点检查只有在可能改变动作时才有价值。对短任务使用一个终点唤醒；未知吞吐使用一次校准唤醒，然后按实际进度估算。状态不变时不通知用户。

唤醒是提醒，不能作为任务终态。分钟级、预先确定的步骤交给普通程序接续，可以减少硬件空闲。

## 6. 推进、诊断与临时委派

消费一个完整结果后，明确它改变了什么，接着完成下一项有价值的已授权交付。报告、状态更新和工具修复只有在服务这个交付时才值得做；不要将局部闭合当作整个项目的终点。

同一故障在没有新证据的情况下重复出现时，停止机械重试：定位尚缺的事实、修改方法或向另一角色提出聚焦问题。是否继续依据实际收益与风险判断，不另设固定重试次数或每步强制复审。

并行任务能明显节省时间或解决具体正确性疑问时，按用户授权与宿主并发能力委派。交代交付物、必要输入、写入范围、资源权限和返回证据；默认不转让主控。主角色整合结果，分歧依据证据解决，不以投票或强制第二次评审替代判断。

## 7. 普通任务程序的最小职责

项目已有运行器能够满足需求时直接复用。需要新脚本时，优先实现：

- 明确输入、输出、运行身份和资源所有者。
- 防止同一任务重复启动，资源释放后接续已确定的步骤。
- 保存进度或可恢复状态，记录真实退出码。
- 终态后写结果与产物入口；失败保留日志和成本。
- 对长任务记录必要的耗时、资源和阶段摘要。

不需要为了通用性先开发分布式调度系统。本仓库没有提供生产任务运行器；具体完成事件、恢复语义和并发机制由项目实现。

## 8. 有价值的记录与归集

尽早确定中心证据位置。小型进度、资源、阶段退出与配置记录可以增量归集；稳定重产物按实际需要归档。记录最新接收时间和路径，保留失败成本。

复用已有稳定证据，不每轮计算所有大文件哈希。高价值稳定产物的最终归档可校验内容一致性；在接收成功、源无读写和删除已授权后才释放源文件。

## 9. 避免失控的限制与文档

新增检查、上限或审批必须服务具体风险或用户要求。写明适用范围和解除条件，用户已授权的动作不反复请示。

身份保护针对输入错配、输出碰撞、错误恢复等真实问题。数值差异是否影响科学结论应由适当比较判断，不自动要求逐位一致。成本记录不是默认费用准入。

历史结论注明范围、负项与未排除解释。旧方向可以因新证据重新开启；不因模板存在某个字段就生成一次低价值工作。

## 10. 发布和维护本模板

代码和模板使用可追溯提交。对行为有影响的变化更新 CHANGELOG，必要时使用 PR。大文件、凭据、私人会话和具体项目账本保留在所属项目，避免混入公共模板。

已安装项目保留自己的修改；模板更新按具体差异合并，不自动重写项目目标、限制、调度或历史。
